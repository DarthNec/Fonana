## 📋 Что произошло

### Проблема
AI предложил **optional chaining** как основное решение для `isCreatorPost` TypeError, пропустив **очевидное и лучшее** решение через передачу `user.id` в `PostNormalizer`.

### Root Cause анализ AI ошибки
1. ❌ **Фокус на симптоме**, а не на причине
2. ❌ **Консервативный подход** - предпочтение минимальных изменений
3. ❌ **Не соединил очевидные точки** - `user` был доступен, но не использован
4. ❌ **Не задал критические вопросы** о существующей архитектуре
5. ❌ **Следовал существующему паттерну** без критической оценки

| Решение | Время | Риск | Архитектура | Безопасность | Поддержка | SCORE |
|---------|-------|------|-------------|--------------|-----------|-------|

| Решение 2 | X мин | Уровень | Оценка | Оценка | Оценка | XX/25 |

**Оценка по каждому критерию:**
- **Время:** 1-5 (5 = быстрее всего)
- **Риск:** 1-5 (5 = минимальный риск)
- **Архитектура:** 1-5 (5 = идеальная архитектура)
- **Безопасность:** 1-5 (5 = максимальная безопасность)
- **Поддержка:** 1-5 (5 = легче всего поддерживать)

**Правило:** Рекомендовать решение с **максимальным SCORE**, не только с максимальной скоростью!

### УРОВЕНЬ 3: Критические вопросы (MANDATORY)

Перед финальной рекомендацией AI **ОБЯЗАН** задать себе:

#### 3.1 "Почему?" (5 раз)
```

   → Потому что не передаётся из API

3. Почему не передаётся из API?
   → Потому что данные могут приходить не через API

4. Почему данные могут приходить не через API?
   → Потому что есть разные источники (cache, direct DB, etc)

5. Почему решение зависит от API?
   → Потому что логика в неправильном месте!
   
🎯 ROOT CAUSE: Логика должна быть в normalizer!
```

#### 3.2 "Что если?" сценарии
```
✅ Что если данные придут из кэша?

✅ Что если API изменится?
✅ Что если нужно использовать на сервере?

→ Для каждого сценария проверить, работает ли решение!
```

#### 3.3 "Существует ли лучше?"
```
✅ ВОПРОС: Может ли существовать более элегантное решение?
✅ ДЕЙСТВИЕ: Потратить 5 минут на мозговой штурм альтернатив
✅ ПРОВЕРКА: Сравнить все варианты по матрице решений

НЕ ОСТАНАВЛИВАТЬСЯ на первом работающем решении!

## 🚨 Red Flags - Когда остановиться и переосмыслить

AI **ОБЯЗАН** остановиться, если видит:

### Red Flag 1: "Быстрое решение"
```
🚨 Если думаешь: "Это самое быстрое решение"
   → СТОП! Проверь: "А самое ПРАВИЛЬНОЕ?"
   
🚨 Если разница во времени < 30 минут
   → Выбирай правильное, не быстрое!
```

### Red Flag 2: "Минимальные изменения"
```
🚨 Если думаешь: "Изменим минимум кода"
   → СТОП! Проверь: "А это решает root cause?"
   
🚨 Если решение = workaround
   → НЕ рекомендуй как основное!
```

### Red Flag 3: "Данные уже доступны, но не используются"
```
🚨 Если видишь переменную в scope, которая НЕ используется
   → СТОП! Спроси: "Почему не используется?"
   → СТОП! Проверь: "Может это и есть решение?"
   
ПРИМЕР: const user = useUser() ← ДОСТУПЕН!
         PostNormalizer.normalizeMany(posts, likes) ← user НЕ передаётся
         🚨 RED FLAG! Почему?
```

### Red Flag 4: "Похожий паттерн существует"
```
🚨 Если видишь функцию: someMethod(data1, data2)
   → СТОП! Проверь: "Что ещё можно передать?"
   → СТОП! Спроси: "Почему только data2?"
   
ПРИМЕР: normalizeMany(posts, likesData)
         🚨 RED FLAG! Почему только likesData?
         → А что ещё можно передать для персонализации?
```

### Red Flag 5: "Логика в разных местах"
```
🚨 Если одна и та же логика в нескольких местах
   → СТОП! Это нарушение DRY
   → СТОП! Найди единое место
   
ПРИМЕР: isCreatorPost вычисляется:
         1. В API route
         2. В lib/utils/access.ts
         3. Ожидается в normalizer
         🚨 RED FLAG! 3 места = проблема!
```

## 📊 Scoring System для решений

### Формула оценки решения:
```
TOTAL_SCORE = (Speed × 0.15) + 
              (Risk × 0.15) + 
              (Architecture × 0.30) + 
              (Security × 0.25) + 
              (Maintainability × 0.15)
```

**Веса объяснены:**
- **Architecture (30%)** - Самый важный! Правильная архитектура = долгосрочный успех
- **Security (25%)** - Критично для production
- **Speed (15%)** - Важно, но НЕ самое важное
- **Risk (15%)** - Важно, но можно митигировать тестами
- **Maintainability (15%)** - Долгосрочная поддержка

### Пример применения:

#### Решение 1: Optional Chaining
- Speed: 5/5 (15 мин)
- Risk: 5/5 (низкий)
- Architecture: 2/5 (не решает проблему)
- Security: 2/5 (уязвимость остаётся)
- Maintainability: 3/5 (workaround)

**SCORE:** (5×0.15) + (5×0.15) + (2×0.30) + (2×0.25) + (3×0.15) = **2.95/5** (59%)

#### Решение 2: Normalizer + userId (предложение пользователя)
- Speed: 4/5 (30 мин)
- Risk: 5/5 (низкий)
- Architecture: 5/5 (идеально)
- Security: 5/5 (безопасно)
- Maintainability: 5/5 (легко)

**SCORE:** (4×0.15) + (5×0.15) + (5×0.30) + (5×0.25) + (5×0.15) = **4.85/5** (97%)

**🏆 ПОБЕДИТЕЛЬ: Решение 2!**

```
