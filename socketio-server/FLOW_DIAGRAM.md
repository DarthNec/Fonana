## Сценарии использования

### Успешная генерация

1. Клиент → API: Запрос на генерацию
2. API → Socket.IO: `status: "started"`
3. Socket.IO → Клиент: Событие `ai-post-updated`
4. Клиент: Показать "Генерация началась..."
5. API: Генерация контента (30-60 сек)
6. API → Socket.IO: `status: "processing"` (опционально)
7. Socket.IO → Клиент: Обновить прогресс
8. API → Socket.IO: `status: "completed"`
9. Socket.IO → Клиент: Показать результат
10. Клиент: Обновить список постов

### Пользователь не подключен

1. API → Socket.IO: POST /notify-ai-post/
2. Socket.IO: `connections.get(userId)` → undefined
3. Socket.IO → API: `404 User not connected`
4. API: Сохранить уведомление в БД для отображения позже

### Множественные посты

1. Клиент запускает генерацию 3 постов одновременно
2. Каждый пост получает уникальный `postId`
3. События приходят с разными `postId`
4. Клиент отслеживает статус каждого поста отдельно
5. UI показывает прогресс для каждого поста

## Преимущества подхода

✅ **Real-time обновления** - мгновенная доставка статуса  
✅ **Не требует polling** - клиент не делает постоянные запросы  
✅ **Масштабируемость** - один HTTP запрос на уведомление  
✅ **Простая интеграция** - обычный POST запрос из API  
✅ **Независимость** - Socket.IO сервер работает отдельно  
✅ **Надежность** - Socket.IO автоматически переподключается  

## Ограничения

⚠️ **Пользователь должен быть онлайн** - если отключен, уведомление не доставится  
⚠️ **Нет истории событий** - события не сохраняются, если клиент офлайн  
⚠️ **Требует WebSocket соединение** - не работает в очень ограниченных сетях  

### Решения для ограничений

1. **Fallback на БД**: Сохранять важные события в БД
2. **Polling backup**: Клиент может периодически проверять статус через API
3. **Push уведомления**: Для критичных событий использовать FCM/APNs
